# M8: Delete, quarantine, Delete later, Delete only (Gate C)

Working method: `CLAUDE.md`. Roadmap: section 5, M8. Spec: 10 (delete flow, quarantine, roots),
10E (delete later, delete only), 11 (dialogs), 12 (API), invariants I3, I4, I7, I9; P4.
This is the first code that changes the phone. Every phone write goes through `Transport.delete`
or `Transport.push`, only from `cleanup/deleter.py` and `cleanup/quarantine.py`, only after an
explicit execute or restore request.

## Features, in build order

1. **Phone writes** (`device/adb_transport.py`, `device/sync2.py`): `delete` (`rm --` one path,
   then stat to confirm), `media_rescan` (best effort broadcast), `push` (SYNC SEND, mtime set).
2. **Migration `0008_delete_runs.sql`**: `delete_run` (source, device, selection hash, state,
   times, typed_required, disposition, manifest paths, counts), `delete_item` (run, phone file,
   path, hash, size, mtime, check result, state), `deletion_log.run_id`.
3. **Preflight** (`cleanup/preflight.py`), streamed through the TaskRunner, cancellable. Per file:
   I3f phone identity (else the run is blocked); present and selected; I3a a verified replica on
   every required destination, the file there with the right size (SSD unplugged: "waiting for
   SSD"); I3c phone size and mtime unchanged (fresh stat); I3d inside a delete root and outside
   the never list; not Protected; not a locked keeper, and the keeper path still present and not
   selected; at least min_age_days old; then I3b the phone's SHA-256 in batches of 40.
4. **Manifest** (`cleanup/manifest.py`, I9): every planned path, size and hash, written with an
   exclusive create and fsync to `DEST_ROOT/.sift/manifests/` on every required destination
   before the first delete; a missing destination blocks the run.
5. **Execute** (`cleanup/deleter.py`): refused unless the preflight finished < 10 min ago for the
   same selection hash, confirm is true, the typed count matches when required, the phone is the
   same, and the manifest is written. One file at a time: re-stat (size, mtime) → delete → stat
   gone → phone_file deleted/absent → deletion_log. A failure is logged and the run goes on; a
   disconnect stops it. At most max_delete_per_run. Then media rescan, then quarantine.
6. **Quarantine** (`cleanup/quarantine.py`): content labelled junk or a near-duplicate copy with
   no present phone path left, disposition quarantine: rename its replicas into
   `DEST_ROOT/.quarantine/YYYY-MM-DD/REL` (same volume), quarantine row, purge_after +30 days.
   Purge at launch and daily on mounted destinations. Restore to the backup (move back) or to
   the phone (push to the original path with its mtime; `_restored` on a clash; phone free space
   must fit the files + 2 GB).
7. **Delete only and Delete later**: the Analyse phone result gets "Delete the backed-up files"
   (source analysis, the verified group only, disposition archive). A "Ready to free" card per
   confirmed, deletable set on Cleanup home (Review and delete → the same flow; Not now).
8. **API**: `POST /api/delete/preflight {source, ids?, analysis_id?, sets?}`,
   `GET /api/delete/runs/{id}`, `POST /api/delete/execute {run_id, confirm, typed_count}`,
   `GET /api/quarantine`, `POST /api/quarantine/restore {ids, to}`, `POST /api/quarantine/purge`,
   `GET /api/cleanup/ready`.
9. **Web**: Delete selected on the review tabs → preflight progress → result (passed and failed
   with reasons) → confirm dialog (count, size, where the backups are, "This cannot be undone on
   the phone", "I have reviewed these files", typed count when required, button with the count)
   → progress → result (space freed). Analyse phone delete button; Ready to free card;
   Quarantine page (list, restore, purge).

## Exit

P4 and the five named tests (stale analysis, provisional entry, unbacked files, waiting for the
SSD, nothing deletes without execute) pass; focused review of the delete code, then the
whole-branch review. Owner, on the real phone: manual checklist item 8 and one delete-only run of
20 verified files. → Gate C.

## Assumptions

- F1. Protected in the preflight: for source `cleanup` (suggestion tabs) the full section 9
  rules apply (camera, screenshots, documents, protected label or folder, unreadable, long
  video), except that a file whose content keeps another present, unselected phone path is not
  blocked (exact copies). For `analysis` the owner chose whole backed-up sets (spec 10E counts
  Camera as deletable), so only the protected label, document words and protected folders block.
- F2. Typed count is required above 200 files (the M11 rule, used here too).
- F3. A quarantined replica's row moves with it (rel_path points into `.quarantine`); purge
  removes the file and then the replica row; content rows stay.
- F4. Media rescan: `am broadcast MEDIA_SCANNER_SCAN_FILE` per deleted path; failure is logged
  only.
- F5. Disposition: `cleanup` quarantine, `analysis` archive (spec); browse/slate arrive later.
- F6. The legacy `/sdcard/WhatsApp/Media/WhatsApp Images|Video|Animated Gifs|Stickers` folders
  are delete roots by default too (spec: "the WhatsApp Media folders").
