# M3: SSD, verify, adoption, confirmation, Analyse phone

Working method: `CLAUDE.md` (native build, tests per feature, one review at the end).
Roadmap entry: section 5, M3. Invariants: I1 never overwrite/delete in a destination; I2 the
staged copy sequence before any replica row; I5 resumable; I7 nothing written to the phone.

## Features, in build order

1. **Migration 0005.** `adopted_file` (dest_id, rel_path, rel_key, size, mtime, hash NULL until
   hashed, state provisional|indexed|duplicate|differs); `problem` (kind, dest_id, rel_path,
   content_hash, detail, created_at, resolved_at); `confirmation` (set_name, device_id,
   created_at, files, bytes, report_path, stale_reason NULL).
2. **SSD presence** (`services/volumes.py`): find the volume by `backup.ssd_volume_uuid`
   (`diskutil info -plist`, injectable runner), require `os.path.ismount`, poll `/Volumes` every
   2 s on a thread, publish `ssd` events, status chip live. SSD destination row created on first
   sight: root = `<mount>/<mac_root folder name>`.
3. **Replicator** (`backup/replicator.py`): copy a replica from one destination to another through
   `StagedFile` (same I2 sequence). `replicate_union(src, dst)` both ways; self-heal drops rows whose
   files are gone first. Runs after the pull in `run_backup` and on SSD plug-in (a `replicate` job).
   SSD missing → summary says "Mac done, SSD pending: N files".
4. **Verify, repair, rebuild** (`backup/verifier.py`, `backup/rebuild.py`): re-hash every replica
   (F_NOCACHE); mismatch → drop the row, add a `problem`, offer Repair from the good copy (a new
   staged copy to a `_HASH8` path; the bad file is left alone, I1). Rebuild = adoption of a
   destination's own tree.
5. **Adoption** (`backup/adopt.py`): walk a chosen folder read-only; `adopted_file` rows
   (provisional); background hash; then `content` + `replica` with the existing rel_path; extra
   copies → `duplicate`; same name different bytes than the phone → `differs` problem.
   `POST /api/backup/adopt`.
6. **Match** (`backup/match.py`): before pulling, look up each new phone file's size in the index;
   candidates → batched phone `sha256`; equal hash links with no transfer. Names are never proof.
7. **Confirmation** (`backup/confirm.py`): per-set report (on phone, verified per destination,
   provisional, missing/changed, failed); Confirmed only when every present file has verified
   replicas on all required destinations and the phone hash agrees; Markdown report in
   `DEST_ROOT/.sift/reports/`; stale on set change or after `confirmation_valid_days`.
   `GET /api/backup/confirmation?set=`, `POST /api/backup/confirm`.
8. **Analyse phone** (`cleanup/analyse.py`): scan without pulling, size-then-hash match, verify
   matches, four groups per set with counts and sizes. `POST /api/analyse/phone`,
   `GET /api/analyse/phone/{id}`. UI: one summary screen, no lists, no delete button.
9. **After a run**: `state.db` copy to `SSD_ROOT/.sift/` (keep 5), "Safe to unplug", Eject
   (`diskutil eject`), backup screen shows SSD bar and Problems list.

## Tests (written after each feature; area tests only until the end)

P3 (run N keeps every file of run N−1); SSD unplug mid-replication; union of two destinations;
`test_adoption_never_modifies_existing_files` (hypothesis over random trees: bytes, mtime, inode,
names unchanged); provisional adoption is not counted as verified; fast adopt mode warns and
hashes; same name and size but different bytes never link; Analyse is read-only (fake journal
shows no mutating call); confirmation goes stale (new file; 31 days via Clock).

## Exit

P3 and SSD-unplug pass; both destinations identical after union; adopting a 20k-file fixture
changes no existing file; Analyse shows correct counts on the fake phone and, read-only, on the
real phone. Full suite, lint, web tests and e2e green. One whole-branch review. → Gate A.

## Assumptions (decided without asking; change any of them later)

- A1. The SSD backup root is `<SSD mount>/<same folder name as the Mac root>`.
- A2. If no SSD was ever configured (`ssd_volume_uuid` empty), `required_destinations` is treated
  as `["mac"]`; once an SSD is configured it is `["mac", "ssd"]` (the setting still wins if edited).
- A3. Adoption works on a whole destination root (the owner points the Mac or SSD root at the old
  folder); rel_paths stay exactly as found. Adopting a folder outside a destination root is M9.
- A4. One replica row per content per destination (existing PK); other copies of the same bytes
  are `adopted_file` rows in state `duplicate`, listed and never touched.
- A5. Repair writes the good copy to a new `_HASH8` path; the corrupt file stays where it is and is
  listed under Problems (deleting it would break I1).
- A6. Polling `/Volumes` every 2 s (no DiskArbitration) is enough.
- A7. `adopt_mode = "fast"` exists only as a setting that warns and behaves like `hash` (spec: no
  name-based mode in v1).
- A8. The Analyse result screen and the SSD/Problems additions reuse the existing Backup screen
  components; no new design work.
